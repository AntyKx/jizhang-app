# 啟動體驗改善：品牌化 Loading + 逾時提示 + 錯誤畫面

日期：2026-08-03

## 背景

延續昨天的根層級 loading 畫面（解決冷啟動空白畫面問題），使用者提出一份完整的啟動體驗規格單。逐條對照這個 App 的實際架構（Next.js Server Components + SSR streaming，不是前端 SPA）討論過後，確認落地範圍：**Loading 畫面品牌化（含逾時提示）+ 全站錯誤畫面**。首頁分區塊 Skeleton（原規格第 8 點）刻意留到下一輪，因為要拆解現有的單一大 `Promise.all` 首頁查詢，工程量夠大，值得獨立處理。

## 處理內容

### Loading 畫面品牌化 + 分階段提示（`src/app/loading.tsx`）
- 改用小熊插畫（`bear-welcome.webp`，跟登入/註冊頁同一張）取代原本的 App 圖示，加上柔和的呼吸縮放動畫（`@keyframes splash-bear-breathe`）
- 文字從單一「正在整理你的帳本…」改成三階段：
  - 0～3 秒：「正在整理你的帳本…」
  - 3～10 秒：「還在讀取，請再稍候一下…」
  - 10 秒以上：「載入時間比預期久」+ 重新整理按鈕
- 逾時判斷改用 `performance.now()`（相對於瀏覽器導覽開始的時間），不是單純從元件掛載那一刻算起——如果網路慢到連 JS 都載了好幾秒才 hydrate，用「掛載後才開始算」會低估使用者真正等待的時間，讓提示語出現得比該出現的時間還晚。
- 沒有做「正在同步共同帳本」這種具體項目提示（原規格第 6 點的字面要求）——Server Component 不會把「目前跑到哪個查詢」這種細節傳到前端，硬做會變成編造的假訊息，改成誠實的通用提示語
- 沒有加「離線進入」按鈕（原規格第 7 點）——這個 App 刻意沒有 Service Worker、資料即時寫雲端，沒有離線可用的東西可以進，硬加只會導向空白畫面

### 全站錯誤畫面（原規格第 10 點）
新增 3 層 `error.tsx`：
- `src/app/(app)/error.tsx`：App 內任何一個頁面自己的查詢/渲染出錯時顯示，導覽列還在（因為 layout 本身沒壞），提供「重新嘗試」+「回首頁」
- `src/app/error.tsx`：根 layout 底下、更外層的錯誤（例如 `(app)/layout.tsx` 自己的驗證/查詢出錯）
- `src/app/global-error.tsx`：連根 layout 本身都壞掉時的最後防線，Next.js 規定這個檔案要自己重建 `<html>/<body>`，刻意寫得極簡（不依賴字型、小熊圖片等任何可能一起壞掉的東西）

以前這三層都不存在，未攔截的錯誤會落到 Next.js 預設畫面，不是這次反映的「一片黑」，但也稱不上是可理解的中文錯誤畫面。

## 已排除、但值得記錄的原因

- **第 5 點（最短顯示 500-800ms 防閃爍）**：這是給前端 SPA 準備的手法，這個 App 是 SSR streaming，資料一好就直接把 loading 畫面換成真內容，故意延遲顯示反而會拖慢原本已經讀完的頁面，跟「讀完立刻進首頁」互相矛盾，沒有做
- **黑畫面根因排查**：HTML/body 背景確認是暖色米白不是黑的；沒有用到 IndexedDB；`localStorage` 只在安裝提示元件裡用、且都在 `useEffect` 裡執行，不會擋畫面；已經有 `ServiceWorkerCleanup` 元件會清除任何殘留的 Service Worker 快取，但那是瀏覽器端 `useEffect` 執行，理論上沒辦法救回「曾經裝過舊版 Service Worker」使用者的第一次載入（舊快取會攔截在我們的清除程式碼有機會跑之前）——這是目前最可能的「偶爾黑畫面」真正原因，但沒辦法從程式面追溯修復已經中招的裝置

## 後續追加：Loading 畫面進場儀式感（同日）

使用者接著問「做假延遲讓開場更有儀式感如何」，討論後排除了「每次固定假延遲」（跟這個 App 一直以來的「越快越好」方向衝突，而且 PWA 留在背景重開根本不會經過這支 loading.tsx，實際效果有限），改成不增加任何等待時間、純粹讓進場動作更有層次：

`src/app/loading.tsx` 加了一段 GSAP 進場動畫（`useGSAP` + `gsap.from(container.children, { stagger: 0.12 })`）：小熊 → App 名稱 → 進度條 → 提示文字，依序淡入＋輕微位移，取代原本「全部同時出現」的靜態畫面。小熊圖片額外多包一層 div——外層負責進場動畫（一次性 opacity/y 位移），內層維持原本連續呼吸縮放的 CSS 動畫，兩者分開避免搶同一個元素的 `transform` 屬性。

## 再後續：換上使用者提供的品牌插畫（同日）

使用者提供一張新的品牌插畫（小熊抱記帳本＋周邊裝飾道具，圖片本身已經包含「小熊記帳」標題跟「正在整理你的帳本…」字樣），要求把 loading 畫面換成這張圖，動畫進度條移到圖片裡那行字的下面。

處理內容：
- 原圖 941×1672、1.5MB 的 PNG，用專案裡已經有的 `sharp`（Next.js image 優化本來就依賴它）縮到寬度 560px 並轉成 WebP，存成 `public/images/bears/bear-loading-splash.webp`，檔案降到約 32KB——這張圖是「網路慢的時候」才會被看到的畫面，圖片本身太大反而會拖慢它想解決的問題，所以刻意壓縮。
- 拿掉原本另外寫的「記帳本」App 名稱文字跟「正在整理你的帳本…」文字——這兩句現在都已經畫在圖片裡了，`initial` 階段不需要再重複顯示一次。
- 進度條位置往上貼齊圖片裡文字下方（用負的 margin-top 把它拉進圖片本身預留的下方留白區域）。
- 3 秒/10 秒後的提示文字（「還在讀取」「載入時間比預期久」）保留，改成只在 `slow`/`verySlow` 階段才額外顯示在進度條下方——因為圖片是靜態的沒辦法動態換字，`initial` 階段的文字已經畫在圖裡了。

## 修正：圖片沒有滿版，看起來像貼紙

使用者反應圖片沒有滿版很突兀。仔細看這張插畫本身就是設計成滿版背景的（四個角落的漸層色塊都是延伸到邊緣的），我一開始卻把它當成一張小圖置中顯示，結果變成一張偏小的卡片浮在 App 本身偏白的背景正中央，看起來像貼紙而不是啟動畫面。改成用 `fill` + `object-cover` 讓圖片撐滿整個畫面當作真正的背景，進度條跟提示文字疊在圖片上方、貼著圖片裡「正在整理你的帳本…」那行字下面的位置。

## 後續（不在這次範圍）

首頁分區塊 Skeleton（原規格第 8 點）：目前 `/record` 是一個大 `Promise.all` 把帳戶餘額、圖表、最近紀錄一次讀完才整頁渲染，要拆成各自獨立的 Server Component + Suspense 需要先梳理首頁的資料相依關係，另外排期。
